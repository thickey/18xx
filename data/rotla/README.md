Prepared 2026-09-26. This is research data for implementing the actual game,
The frozen real setup catalog is `runtime-map-v1.json`; the original prototype
definitions remain separate for saved-game replay.

## The generator provides the whole set in one request

The client uses **GET**, not POST:

```text
https://lost-atlas-api.fly.dev/boards/{seed}?variant=std&random_minors=false&random_start_tile=false&landmarks=false
```

It sends the key supplied in the user's URL as a Bearer authorization header.
The key is deliberately not copied into this catalog. The inspected frontend
identifies itself as `v1.4.0 production`.

Both saved samples (3722698 and 3722699) contain all 33 pieces. Further random
sampling is unnecessary for basic terrain coverage. `random_start_tile=false`
means **fixed start piece 25**, not omission of a starting piece. `random_minors`
is relevant to the Short variant; Standard includes all 11 printed minor homes.
Adaptive has no fixed printed home.

`tile_id` identifies a physical copy; `setup_tile` identifies one of its three
hexes. `tri_hex_id` is a placement index and must NOT become a permanent piece ID.
The printed numbers run 1-28, with two copies of each of 12-16. API IDs 120/121,
130/131, etc. distinguish those copies. Preserve strings and leading zeros.

Cube coordinates are returned as `x_y_z`, with x+y+z=0. The client draws a pointy
hex grid using x and y as axial coordinates. The research catalog translates
Hex1 to the origin, then chooses the lexicographically smallest of its six
rotations while preserving Hex1/2/3 labels and handedness. It never reflects a
piece. This is a local coordinate convention, not the artwork's printed pose.
The current engine prototype uses flat hexes, so display/edge conversion must
be established before importing this geometry into the renderer.

`canonical_facing` follows the client's orientation lookup: nn, ne, se, ss, sw,
nw advance by two positions for each API `rotation` value, followed by the
catalog's geometry rotation. The result matches across both seeds. It is a
source artwork direction, **not a track-exit list or an engine edge number**.
Original coordinates, orientations, rotations and placement indices are retained
under observations for auditing.

## Capital overlays are not permanent piece features

The first seed labels 06_Hex2, 151_Hex1 and 161_Hex1 as capital cities. The second
labels 04_Hex1, 06_Hex2 and 08_Hex3. The physical sheet shows ordinary cities in
these positions. `map-pieces.json` normalizes all of them to `standard_city`;
`validation.json` retains each sample's capital selections. This prevents a
random generated setup from accidentally redefining the physical supply.

Likewise, the three capital project pieces are instructions in the draw stack,
not three more terrain triangles. The 33-piece catalog does not include the
12 optional single-hex overlays or the Landmarks expansion.

## Important source discrepancies

- The PDF component sheet is **PDF page 3 / printed page 2**. It shows 33 map
  pieces and 135 track tiles. PDF page 8 explicitly uses a 5-player-only extra
  3-train, identifying the older rule treatment even though no revision number
  has been established.
- The inventory header reports a 2026 kit changing that extra 3 to **4+ players**
  and adding a **4+ player 6-train**. Its train table still describes the older
  counts. The catalog keeps the old table and revision delta separate.
- The inventory lists 36 minor certificates / nine sets, yet lists 12 minors
  with four certificates each. Preserve this as a source inconsistency; do not
  silently turn the 36 into the implementation's certificate count.
- The inventory lists one round/cycle marker, while PDF page 3 shows two.
- Its map summary says 105 hexes, while the generated base tri-hex set has 99.
  Optional overlays may explain some differences, but the exact basis of that
  aggregate count has not been reconciled.
- FWTWR's track IDs are reference labels assigned by the author: the physical
  track tiles are unnumbered. Even familiar numeric IDs are not yet verified
  against this repository's track geometry, revenue and city-slot definitions.
  LA1-LA7 are author-assigned custom IDs. Brown in that chart means purple in
  the game; both colors are retained.
- The upgrade chart calls tile 11 “Tunneling”; tile 11 is Spacious and Tunneling
  is on tile 8. Some map-image alt text also uses the wrong tile number. The
  transcription preserves source labels and flags the bad row.
- Upgrade adjacency is necessary but not sufficient for legality. Rotation,
  reachability, preserved connections, symbols, capital restrictions, supply
  and company abilities still apply. Mining has a special connection-preserving
  rule; blindly applying ordinary city-track geometry would be wrong.

## Runtime map integration

The complete real map supply is integrated through the versioned Ruby catalog
`lib/engine/game/g_rotla/map_catalog.rb` and `real_map_builder.rb`. See
`runtime-map-v1.json` for its cells, home metadata, approved special records and
ordinary-cell rules. `MAP-INVENTORY.md` remains the physical-piece index. Run
`python3 scripts/rotla/build_runtime_catalog.py --check` to check catalog drift.
New games use real setup; old prototype/review actions retain their original
definitions. The normal map and previews use the same tile codes.

Basic cities and ordinary homes start at revenue zero with one slot; mountains
and the Tunneling home cost 40. The default destination schedule is the supplied
rulebook's recommended 30/40/70/100 card, shared across all destinations.
Capital projects convert already placed basic cities, excluding homes/capitals.
Short/Long and two/three-player Micro setup are supported, including an optional
finishing phase for twelve blank hexes around minor homes. See docs/ROTLA.md
for the timing interpretation. Other destination cards remain future work.

`reference-map-3722698.json` preserves the first generator sample as a complete
coordinate regression fixture. It does not claim to be a publisher preset.

## Reproduce and validate offline

From the repository root:

```sh
python3 scripts/rotla/prepare_data.py
```

Only Python's standard library is required; no live API calls are made. The
script rebuilds the derived JSON from the saved HTML and two saved board
responses, checks coverage, cube/triangle geometry, terrain/facing consistency,
shares, tokens, tile totals and upgrade references, and records source hashes.
`rulebook-facts.json` is hand-curated and is intentionally not overwritten.
The rulebook PDF must remain at the repository root for its provenance hash.

Source snapshots retain the source authors' text and markup for audit; they
are not original project artwork or an implied license to redistribute artwork.
The preparation script does not overwrite the frozen runtime catalog.
